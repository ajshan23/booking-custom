# Flowflex API-node integration

## Required values

Configure a backend base URL reachable from the Flowflex runtime, a service API key, customer reference/name/email and meeting type. Customer timezone is optional: the backend infers a primary IANA timezone from an international phone number, while an explicitly supplied timezone overrides that inference. The Google organizer connects once outside the flow, using the admin setup procedure in README.

All API nodes use an Authorization header with the service key. Do not use the Google refresh token or admin key. The backend does not authenticate customer identities itself; it trusts the authorized Flowflex service caller to associate session/booking IDs with the right contact. Do not expose these endpoints directly in a public browser client using the shared service key.

## Response mapping

The existing API activity wraps responses as:

```json
{
  "ok": true,
  "status": 200,
  "headers": {},
  "data": {
    "status": "slots_available",
    "sessionId": "...",
    "message": "Available times ...",
    "data": { "slots": [] }
  }
}
```

If the API node alias is `availability`, then:

```text
HTTP status:          {{availability.status}}
Business status:      {{availability.data.status}}
WhatsApp message:     {{availability.data.message}}
First slot ID:        {{availability.data.data.slots[0].id}}
```

Use the actual aliases generated by your flow editor. These aliases are illustrative, not an importable flow definition.

## Flow sequence

1. Ask name/email and meeting type. Email validation failure should loop to an email question.
2. **Create session API node**: POST `/v1/sessions` with name, email, customerRef and meetingType. Omit timezone to infer it from the phone country; read the result from `response.data.data.timezone` and state it explicitly to the customer.
3. Ask the preferred date as free text.
4. **Interpret API node**: POST `/v1/sessions/<sessionId>/interpret` with the reply in `text`.
5. Branch on `response.data.status`. For `needs_clarification` or `invalid`, send `response.data.message`, wait for the reply, and call the same interpretation endpoint with the same session ID. For `resolved`, continue.
6. **Availability API node**: POST `/v1/sessions/<sessionId>/availability` with `{ "page": 0 }`. Keep a `slot_page` flow variable and increment it only after a `__next__` selection; other loop iterations may be date or confirmation steps.
7. If `no_slots`, collect a new date and return to interpretation. Otherwise pass `data.slots` to a dynamic list. Non-final pages contain nine real choices plus `__next__`; final pages contain up to ten real choices.
8. Route a selected `__next__` ID to a state update that increments `slot_page`. Route every real slot ID to the selection API and move the state to confirmation.
9. **Select API node**: POST `/v1/sessions/<sessionId>/select` with `{ "selection": "<reply>" }`. Save the returned `data.confirmationToken` and send the returned confirmation message.
10. Wait for an explicit Confirm button. Not now exits and Talk to team hands off. Never call the booking node for arbitrary replies or a timeout.
11. **Book API node**: POST `/v1/sessions/<sessionId>/book` with `confirmed: true`, the saved confirmation token and an Idempotency-Key header such as `onboarding-<sessionId>`. Keep that key unchanged on retries.
12. Send success only for `confirmed` with a non-empty Meet link. For every pending or failed result, send the backend message and hand off without creating another booking.

The confirmation token identifies the details shown to the customer. It is not a substitute for collecting their confirmation in the flow.

## Booking branches

| Business status | Flow action |
| --- | --- |
| `confirmed` | Send full date/time/timezone and `data.meetUrl`; the email invite was requested |
| `creating`, `reconciling` | Send the processing message once; wait 5–10 seconds and GET `/v1/bookings/<bookingId>` |
| `meet_pending` | Say the meeting is booked and the link is being prepared; poll the same booking |
| `meet_failed` | Hand over to support; do not create a replacement meeting automatically |
| `slot_unavailable`, `slot_expired` | When `data.canReselect` is true, reuse the reopened session and return to date/time selection |
| `failed` | Explain the failure and hand over; do not automatically create a replacement booking |
| `invalid_selection` | Ask for a number from the current choices |
| `invalid_input` | Re-ask the relevant field, e.g. email |
| `google_reconnect_required` | Alert your operator and hand over to support |
| `interpretation_unavailable` | Offer YYYY-MM-DD input or hand over |
| `session_changed` | Avoid using stale choices; restart the session if you have no current booking ID |

The practical import hands pending states to the team instead of polling inside WhatsApp. The backend continues reconciliation every 30 seconds. A larger production flow may poll the same booking ID, but must never call `/book` again with a different idempotency key. If `data.errorCode` requests review or Google reconnection, route to support.

## Cancellation

Associate the saved booking ID with the original contact. Ask the customer to confirm cancellation, then POST `/v1/bookings/<bookingId>/cancel`. A repeat cancellation returns the existing cancelled result. If the status is `cancelling`, poll that booking until it settles. Calls while creation is uncertain return `booking_pending`; wait for reconciliation first.

## Operational notes

- HTTP failures with a response are available for branching in the existing API node. Network failures may be retried by the runtime, so the booking Idempotency-Key is essential.
- Do not send `null` as a Meet link. `meet_pending` and `meet_failed` are different from a confirmed meeting with a usable link.
- Check the backend business status inside the response body, not only the outer HTTP `ok` flag.
- WhatsApp follow-ups outside the customer-service window need an approved template; configure this in Flowflex if a delayed response is sent.
- For campaign-triggered flows, publish the updated campaign after configuring the flow so the active snapshot includes these API steps.
